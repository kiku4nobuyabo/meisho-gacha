# データ構造と保守メモ

## ファイル分離の方針

永続データは `data/record.json` 1ファイルにまとめ、下記のコレクションで論理的に分離する。
GitHub Contents APIの1回の更新を保存単位にし、シーズンだけ更新されてイベントが欠ける等の分割保存を避ける。
アプリ本体と記録リポジトリは分離。外部APIはGitHubのみ。

| 項目 | 意味 |
|---|---|
| schemaVersion | 1。未対応バージョンは読み込みを停止 |
| datasetId | 記録全体の識別UUID |
| revision | 変更ごとのUUID。日時を比較して上書きしない |
| activeSeasonId | 最新シーズンのID |
| generals[] | 現在の武将マスター |
| seasons[] | シーズン名、開始日時、開始時の武将マスターコピー |
| pools[] | シーズンID、版名、日時、武将情報の完全コピー |
| events[] | 全シーズンの操作ログ。配列順を操作順として扱う |

武将フィールド：`id, name, reading, faction, rate, note`。
rateは `high / low / unknown`。unknownの武将は排出ONにできない。
現在排出中かは現在シーズンの最新プール内のIDで求める。マスターとプールに重複したON/OFFフラグを保存しない。
新規武将は現在プールに追加されないため、OFFになる。

## 操作イベント

通常：`{id,type:"pull",seasonId,poolId,at,deviceId,result:"normal"}`

S：上記のresultが `"S"`、さらに `general` に記録当時の武将情報をコピーする。

取消：`{id,type:"undo",seasonId,at,deviceId,targetId}`

project()はイベントを登録順に再生し、UNDO対象を有効操作スタックから取り除く。
残った有効操作を再計算して、総回数、S天井、高排出連続、S排出内訳、S間隔、平均S間隔を返す。
集計キャッシュを正本にしない。Sの1回分を二重に加算する経路を持たない。

- 非Sはpityが29未満の場合だけ許可。
- Sは1回加算した値を間隔として記録し、pityを0に戻す。
- 高排出Sはstreakが5未満の場合だけ許可。
- 低排出Sはstreakを0に戻す。
- UNDOは現在シーズンの直近有効操作IDだけを受け付ける。
- 日時はUTC ISO 8601で保存、UIはAsia/Tokyoで表示。日時では並べ替えない。

## 不変スナップショット

過去pool.generalとevent.generalをマスターへの参照だけにしない。
マスター編集時は、現在排出中の武将に影響する場合だけ新しいプール版を作る。
新シーズンは現マスターをinitialGeneralsへコピーし、未設定の初期プールから開始。
初期プール編集UIの選択候補は前シーズンのON対象を引き継ぐが、保存まで新シーズンのプールは成立しない。
入力途中のキャンセルでガチャイベントは発生しない。シーズン名確定後は正式切替済みで、初期プール設定だけが未完了となる。

## 端末保存

localStorageのアプリURL別キーに以下のenvelopeを保持する。

`{data, dirty, baseSha, remoteKey, lastSync}`

毎回データをvalidateしてから保存。保存失敗を入力成功として扱わない。
既存JSONの破損を検出した場合、初期データで置き換えず復旧画面で停止する。
接続前・インポート前・競合解決前のバックアップを最大5件、別キーに残す。
トークンは別の設定キー、または保存しない場合はsessionStorage。エクスポート対象外。
公開ソースにトークンの値・記録データを埋め込まない。画面の動的文字列はHTMLエスケープする。

## 同期

1. 端末保存を先に完了。
2. GET ContentsでGitHubの現在SHAとデータを取得。
3. クリーンなら同じdatasetIdのリモートを読み込む。
4. 未同期なら取得SHAとbaseShaの一致を確認。
5. 同じSHAならPUT Contents。リモート更新にはSHAを必ず指定。
6. 競合したら端末・GitHubの双方を保持。自動上書き・自動合流しない。
7. PUT成功後の応答欠落は、次のGET内容と端末データの完全一致で回復。

APIエラー/タイムアウトではdirtyと端末データを維持。
別datasetId、リモート削除も競合扱い。
同一端末のタブはWeb Locks APIで保存・同期の処理を直列化し、保存時のrevisionも確認する。
Web Locks非対応ブラウザで複数タブを同時操作する場合の完全な原子性は保証しない。最新Chrome/Safariを推奨。
接続時はリポジトリがPrivateであることとブランチの存在を確認。
自動同期は起動・focus・online・visibility復帰・表示中45秒間隔。ただし開いている管理ダイアログを自動更新で壊さない。
保存・同期中は次の入力を受け付けない。同期通信は15秒でタイムアウトする。

## 競合時の選択

画面に端末側・GitHub側のシーズンと回数を表示。
両データを一つのJSONでエクスポートでき、復元時にはどちらかを選べる。
「GitHubを使う」も「端末でGitHubを置換」も、選択画面を開いた時のリモートSHAをもう一度検証して実行する。
GitHub側を置換する場合もSHA指定PUTのため、確認後に第三の更新が起きればAPIが拒否する。
両方を自動マージしないため、捨てる側の未反映入力は手動再記録が必要。

## 拡張時

旧schemaVersionを受け取る明示的なマイグレーションを作ること。
過去スナップショット・eventsをマスターの最新内容に再連結しないこと。
現在の950,000バイト同期上限を拡張するなら、Git Blobs API等の大きなJSONの取得と保存単位を一緒に検討する。
日々4回程度でも全履歴・プールコピーは増えるため、無制限容量は想定しない。
